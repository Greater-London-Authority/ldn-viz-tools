# RFC 0003 — Token pipeline and outputs

## Summary

The token pipeline in `packages/themes` was built for v3, with Tailwind as its main consumer. It emits nine CSS files, a set of Tailwind extension files and a Tailwind preset whose plugins hold most of the typography and flow behaviour. A consumer who doesn't use Tailwind gets the custom properties but none of the classes the specification describes.

This RFC makes CSS custom properties the single public surface of the system. Everything else is either a window onto those properties (the CSS classes and the Tailwind preset) or an export of their resolved values (JavaScript and Sass). The classes the specification names (typesets, roles, flow, elevation, usage aliases) are generated by Style Dictionary as plain CSS, so they work the same with or without Tailwind. The pipeline is also rebuilt around the new Figma export (`lcd-ds.tokens.json`), and the spec tooling is updated to match.

These changes are planned together because they share one boundary. The file names, the class generator and the spec scripts all depend on the same decision about what the package emits.

## Motivation

- **Tailwind is a hidden dependency.** The specification says the system can be used "anywhere", and its second tier ("adapting existing systems") promises alias classes. Today, typography and flow classes exist only as Tailwind plugins (`tailwind-custom/typography/*.cjs`, `tailwind-custom/flow/flow.cjs`). A team using plain CSS, Sass or another framework cannot use them.
- **Too many files to import.** A full setup imports nine CSS files (`primitives`, `primitive-scale`, `light`, `dark`, `spacing`, `grid-spacing`, `flow`, `typography`, `shadows`) in a set order, and then also needs the preset. The file split follows the pipeline's internals, not anything a consumer chooses between.
- **Typography is maintained by hand.** About 1,100 lines of `contexts.cjs`, `responsive.cjs`, `roles.cjs` and `semantics.cjs` map token names to classes by hand. The new token grammar (typeset × role × size × property × breakpoint) is regular enough to generate them. RFC 0002 will rename typesets and roles. Generating the classes from tokens and a short naming config makes those renames cheap.
- **The new Figma export doesn't match the pipeline.** The collection names, the mode structure, the shadow and elevation tokens and several keys have all changed. The filters and formats in `sd.build.js` are written for the old export and will drop or mis-group tokens.
- **The spec tooling is coupled to the current file names.** `scripts/spec_common.py`, `gen_spec.py` and `check_spec.py` parse `typography.css`, `spacing.css`, `flow.css` and `primitive-scale.css` and check that each `tw-extend` file is used. `SPEC-CHANGE-PROTOCOL.md` still names the old export file and asks for the gitignored `styles/` folder to be committed.

If nothing changes, the v4 classes from RFC 0002 will be written as more Tailwind plugin code. Non-Tailwind consumers will stay unsupported, and every rename will need the hand-maintained mappings updated in step.

## Scope

1. Token source and parsing
2. Outputs and distribution
3. System classes as generated CSS
4. Tailwind preset
5. Value exports (JavaScript and Sass)
6. Spec tooling and governance

## Non-goals

- **Class and token names.** RFC 0002 decides the names of typesets, roles, densities and archetypes. This RFC builds the generator so that those names come from one config file, and uses the names in the current specification as placeholders.
- **Token values.** No colour, spacing or type value changes here.
- **Tailwind v4.** The preset stays on Tailwind v3. The model proposed here (properties first, a thin theme mapping) moves cleanly to v4's `@theme inline` later, but that migration is a separate piece of work.
- **Component packages.** `ui`, `charts`, `maps` and `tables` only change their import lines, and drop any use of plugin-only classes that move to `system.css`.
- **Figma structure.** The export is taken as it is. Fixes needed on the Figma side are listed under workstream 1 and in the open questions.

## Workstream 1 — Token source and parsing

- **The change.** Now: the parser and filters are written for `design-tokens.tokens.json`. Shadows sit at the top level and are picked out by excluding every other category. Proposed: the pipeline reads `lcd-ds.tokens.json` and normalises it in one parser step before any filtering:
  - **Mode-qualified references.** Every alias carries the mode name of the collection it was exported from (`{primitive.xl.typography.scale.14}`, `{primitive.dark-mode.color.static.white}`). The parser strips the second segment of references into `primitive`. The current replacement list already covers `mode 1`, `light-mode`, `dark-mode` and `base` to `2xl`; it becomes a single pattern so that a new mode name doesn't break the build.
  - **Mode levels.** `semantic-color.{light-mode,dark-mode}`, `semantic-typeset.{base…xl}` and `semantic-grid.{base…2xl}` become `mode.{light,dark}`, `typography.{bp}` and `grid.{bp}`. The `semantic` prefix is removed, as the naming grammar requires.
  - **Shadows by type.** Shadows and elevation are selected by `type: 'custom-shadow'`, not by category. Multi-layer shadows (the `0`/`1` children) are grouped by their parent path, so `primitive.shadow-md.{0,1}` becomes one `--shadow-md` value. The primitive, Tailwind and JS filters exclude the shadow type.
  - **Units.** Spacing, type scale, line height and breakpoint values arrive unitless. They become `px` in the token graph ([0004](../decisions/0004-spacing.md)), and `rem` where the spec asks for it, by a transform keyed on path, not by hand in each format.
  - **Key normalisation.** Keys are kebab-cased generically, so `focus ring`-style special cases are no longer needed.
- **Why it has to break.** The old export is gone. Patching the old filters to the new shape would keep the exclusion-list approach that caused the shadow problems.
- **Affected surface.** `sd.build.js` (parser, `renameKeysDeep`, filters, `groupShadows`, `formatShadows`), `sd.config.json` sources.
- **Migration.** None for consumers on its own. The emitted property names follow the specification's grammar, and any differences from the current names are listed with workstream 2.
- **Change-sets.** (1) Parser and normalisation, with a test that every reference resolves. (2) Filters by type. (3) Shadow and elevation formats.
- **ADRs this produces.** _Token export and parsing_ (amends [0001](../decisions/0001-sources-of-truth.md), which names the export).

## Workstream 2 — Outputs and distribution

- **The change.** Now: nine CSS files, four `tw-extend` files, a JS module and a docs module, all under `styles/` and imported by path. Proposed: a small set of named outputs, each with one job, published through a `package.json` `exports` map.

  | Output                  | Contains                                                                                                                           | Kind         |
  | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------ |
  | `reset.css`             | Element defaults at zero specificity (`:where()`), for consumers without Tailwind's preflight (workstream 3)                       | Base         |
  | `tokens.css`            | Every custom property: primitives, light mode on `:root`, dark mode on `.dark`, spacing, grid, flow, typography, shadow, elevation | Source       |
  | `system.css`            | Every class the specification names (workstream 3)                                                                                 | Window       |
  | `index.css`             | Imports `reset.css`, `tokens.css` and `system.css`, in that order                                                                  | Convenience  |
  | `tailwind`              | The Tailwind preset (workstream 4)                                                                                                 | Window       |
  | `colors.js`             | Resolved colour values for light and dark                                                                                          | Value export |
  | `scss`                  | Sass variables and maps with resolved values                                                                                       | Value export |
  | `docs/tokens/tokens.js` | Every token with its name, resolved value, type and description, for the documentation site                                        | Value export |

  Consumers choose between three set-ups, which match the specification's tiers:
  1. **Full system:** `@import '@ldn-viz/themes/index.css'`, plus the Tailwind preset if the app uses Tailwind.
  2. **Tokens only:** `@import '@ldn-viz/themes/tokens.css'`, for teams that want the properties but write their own classes.
  3. **Values only:** `colors.js` or `scss`, for tools that cannot read custom properties.

  `typography` and `flow` are not split into separate files. `typeset-longform` adds `flow-spacious`, so the flow selectors and the typeset selectors have to ship together.

- **Why it has to break.** Import paths change. An `exports` map also blocks deep imports that it doesn't list, so any consumer importing `@ldn-viz/themes/styles/...` or `ldn-theme.cjs` directly breaks. The old paths are not kept: the migration table maps each one to its replacement.
- **Affected surface.** `sd.config.json` platforms and files, `package.json` (`exports`, `files`), `apps/web/src/app.postcss` and `apps/storybook/src/app.postcss` (nine imports each), the six `tailwind.config.cjs` files, the colour-token importers (`packages/ui/src/lib/theme/themeState.svelte.ts`, `packages/maps/src/lib/loadTestLayers.ts`, `packages/utils/src/colors/scales.ts`, the Storybook theme and tests), and the docs page `apps/web/src/content/design-system/foundations/design-tokens.md`.
- **Migration.** A major release of `@ldn-viz/themes`, with a migration table from the old paths and property names to the new ones. The table also lists the property names that workstream 1 changed.
- **Change-sets.** (1) New outputs emitted, `exports` map, internal imports moved, old outputs removed.
- **ADRs this produces.** _Distribution and outputs_ (new).

## Workstream 3 — System classes as generated CSS

- **The change.** Now: typography contexts, roles, responsive values and flow rules are Tailwind plugins (`addComponents`, `@screen`) maintained by hand. Proposed: Style Dictionary generates every class in the specification as plain CSS in `system.css`:
  - **Typesets.** Each typeset class sets the role properties for its typeset, with a media query per breakpoint. Role classes (`.{role}-{size}`, `.eyebrow`) read those properties. Inheritance gives "the innermost typeset wins" with no extra rules.

    ```css
    .typeset-longform {
    	--title-lg-font-size: var(--typography-base-longform-title-lg-font-size);
    	/* … */
    }
    @media (min-width: 640px) {
    	.typeset-longform {
    		--title-lg-font-size: var(--typography-sm-longform-title-lg-font-size);
    	}
    }
    .title-lg {
    	font-size: var(--title-lg-font-size);
    	/* … */
    }
    ```

    Media queries cannot use `var()`, so the breakpoint values are written in as literal `px` from the breakpoint tokens at build time.

  - **Flow.** The context classes (`flow-spacious`, `flow-standard`, `flow-compact`), the owl rules and the `.mt-flow[-{step}]` and `.gap-flow[-{step}]` utilities. The selectors include `.typeset-longform` wherever they include `.flow-spacious`.
  - **Emphasis.** `.text-strong` and `.text-soft`.
  - **Elevation.** `.elevation-0` to `.elevation-6`.
  - **Usage aliases.** One class per entry in the Figma `usage` style set, each pointing at a role.
  - **Layout and base.** The grid classes (`.container-fluid`, `.grid-gutter`) and the base focus styles, which today live in the preset.

  Class names come from one small config file (typeset, role, density and step names), so RFC 0002's renames change the config, not the generator.

- **Why it has to break.** The plugin-only classes move out of Tailwind. For Tailwind consumers the class names don't change, but responsive variants such as `md:mt-flow-loose` stop working once the flow utilities are plain CSS.
- **Affected surface.** `tailwind-custom/typography/*` and `tailwind-custom/flow/*` (removed), `ldn-theme.cjs` plugins, the `custom/typography` and `custom/flow` formats in `sd.build.js`, and any component markup that relies on Tailwind variants of flow utilities.
- **Migration.** A scan for variant-prefixed flow and typography classes (`sm:`, `md:`, `hover:` and so on) across `packages`, `apps` and `.md` content. Each use is either replaced with a plain class or kept by emitting that variant explicitly. Visual comparison of Storybook and the docs site before and after.
- **Change-sets.** (1) Naming config and generator for typesets and roles. (2) Flow. (3) Elevation, emphasis, aliases, layout and base. (4) Plugins removed from the preset.
- **ADRs this produces.** _System classes_ (new). _Flow_ amendment to [0005](../decisions/0005-flow.md), whose consequences name `tailwind-custom/flow/flow.cjs` and `tw-extend/flow.cjs` as the home of flow rules and utilities.

## Workstream 4 — Tailwind preset

- **The change.** Now: the preset extends the theme from four `tw-extend` files and adds five plugins. Proposed: the preset only maps the Tailwind theme onto the custom properties (colours, spacing, `screens` from the breakpoint tokens, `boxShadow` from the shadow tokens, font families). It is generated as one file, not assembled from four, and adds no plugins. The form styles move to `system.css` as plain CSS, so they are available without Tailwind like every other class, and `@tailwindcss/forms` is dropped.
- **Why it has to break.** The plugins move to `system.css` (workstream 3), so a Tailwind consumer must also import `system.css` or `index.css`.
- **Affected surface.** `ldn-theme.cjs`, `tw-extend/*.cjs`, the six `tailwind.config.cjs` files. `@tailwindcss/typography` is listed in `packages/tables/package.json` but not used, and is removed.
- **Migration.** Tailwind configs change their preset import path. Apps add the `system.css` import.
- **Change-sets.** (1) Generated preset. (2) Configs moved.
- **ADRs this produces.** Part of _Distribution and outputs_.

## Workstream 5 — Value exports (JavaScript and Sass)

- **The change.** Now: `styles/js/color-tokens.js` is emitted as a JS module. `styles/sass/*.scss` exist on disk, but no generator in `sd.build.js` or `sd.config.json` produces them, so they are stale. Proposed:
  - `colors.js`, rename the existing JS module, with resolved light and dark values.
  - Sass is generated: resolved values as `!default` variables, with maps for modes and breakpoints. Sass is a value export, not a window onto custom properties. Teams adapting the system to another stack need the values, and `var()` references would tie them back to `tokens.css`.
- **Why it has to break.** The Sass files change shape once they are generated. No Sass consumer has been found in this repo.
- **Affected surface.** `custom/js` format, a new Sass format, `styles/sass/`, and `packages/utils/src/colors/scales-colorRampThresholds.test.ts`, which imports a `styles/js/theme-tokens` module that no longer exists.
- **Migration.** JS importers move from `styles/js/color-tokens.js` to `colors.js`. Sass consumers, if any are found, get a mapping in the changelog.
- **Change-sets.** (1) JS. (2) Sass generator. (3) Stale Sass files removed.
- **ADRs this produces.** Part of _Distribution and outputs_.

## Workstream 6 — Spec tooling and governance

- **The change.** Now: the scripts parse individual CSS files, `gen_spec.py` writes blocks (`prose-matrix`, `css-appendix`) that no longer match the spec's markers (`longform-matrix`, `product-matrix`, `alias-table`, `spacing-table`, `flow-table`), and `check_spec.py` checks Tailwind plugins. Proposed:
  - Style Dictionary also emits one resolved, flat `tokens.json` for tooling. The scripts read that file instead of parsing CSS, so they no longer depend on how CSS files are split or named.
  - `gen_spec.py` writes the blocks the spec now marks.
  - `check_spec.py` checks `system.css` for every class the spec names, instead of checking Tailwind plugins and `tw-extend` usage.
  - `adr_check.py`, specified in `ADR-LIFECYCLE.md` but not yet written, is added and run with the other checks. `RULES.md` stays hand-written: editing it is the moment someone restates a decision as a rule, and that friction is a useful check. The script catches the structural drift: front matter, symmetric links, statuses against folders, the amendment limit, and every live ADR cited in `RULES.md`.
  - `check_spec.py` also checks every class `RULES.md` names against `system.css`, which catches the content drift the citation check can't. `RULES.md` names the default flow utility `.mt-flow`, for example, while the generator and markup use `.mt-flow-default`.
  - `SPEC-CHANGE-PROTOCOL.md` names `lcd-ds.tokens.json`, and settles whether `packages/themes/styles/` is committed or stays gitignored (see open questions).
- **Why it has to break.** The files the scripts read are removed in workstream 2.
- **Affected surface.** `scripts/spec_common.py`, `gen_spec.py`, `check_spec.py`, `verify_build.py`, `scripts/adr_check.py` (new), `governance/SPEC-CHANGE-PROTOCOL.md`, `packages/themes/.gitignore`.
- **Migration.** None outside the team.
- **Change-sets.** (1) Tooling JSON output. (2) Scripts. (3) `adr_check.py`. (4) Protocol.
- **ADRs this produces.** None. Process changes go in governance, not ADRs ([writing documentation](../writing-documentation.md)).

## Verification

- A build test that fails if any reference doesn't resolve or any token in the export is not emitted by some output.
- `verify-build` and `check` pass at the end of each phase.
- A plain HTML page that imports only `index.css` (no Tailwind) shows every typeset, role, flow context, elevation level and usage alias correctly, in light and dark modes and at each breakpoint.
- Screenshots of Storybook and the docs site are compared before and after phase 3.
- The emitted custom property names are checked against the grammar in the specification, and every class the spec names exists in `system.css`.

## Communication

- **Consuming teams:** the new import model (three set-ups), announced before the major release, with a migration table from the old paths and property names to the new ones.
- **Teams not using Tailwind:** a short getting-started page showing a plain CSS set-up. For many of them this is the first supported route.
- **Designers working in Figma:** the export conventions the pipeline now relies on (all modes exported, kebab-case keys, a `usage` style set), recorded in the protocol.
- **Public docs site:** the design tokens page rewritten around the new outputs, as part of RFC 0002 workstream 4.

## Risks

- **Cascade order with Tailwind v3.** If `system.css` uses native `@layer` blocks, Tailwind v3's unlayered output (including preflight's element resets such as `h1 { font-size: inherit }`) wins over every layered rule regardless of specificity. Either `system.css` is shipped unlayered, or Tailwind consumers import it inside Tailwind's own `@layer components`. This needs a decision and a test page before phase 3.
- **Lost Tailwind variants.** Utilities moved out of Tailwind lose `md:`, `hover:` and similar prefixes. The phase 0 scan sizes this.
- **External deep imports.** Consumers outside this repo may import `styles/*` paths. These break on upgrade, so the migration table has to cover every path the package published.
- **Figma export drift.** The pipeline now depends on Figma exporting every mode. A partial export (one mode per collection) builds without error but silently drops light mode or breakpoints. The build test in Verification catches this.
- **Generated selectors grow.** Typesets × roles × sizes × breakpoints produces a large `system.css`. Its size should be measured in phase 3 and compared with the current Tailwind output.

## Open questions

1. Is `system.css` layered, and if so, how do Tailwind consumers import it (see Risks)?
2. Which typeset applies when no `typeset-*` class is set: one set on `:root`, or none?
3. Do `.mt-flow-*` and `.gap-flow-*` stay in the Tailwind theme as well, to keep responsive variants, or move entirely to `system.css`?
4. Is `elevation` emitted as its own custom properties (`--elevation-{n}`), or only as classes pointing at the shadow tokens? In the export, elevation values are copies of the shadow values, not aliases, so the two can drift.
5. Is `packages/themes/styles/` committed, so that `verify_build.py` compares against something, or does it stay gitignored with verification against a fresh build?
6. Font weight `light` is still in the export, while the spec lists four weights. Is it removed in Figma or filtered out in the pipeline?
7. The `usage` style set is not in the export yet. Until it is, are the alias classes listed in the naming config?
8. ~~Should the `exports` map keep `ldn-theme.cjs` at its current path permanently, as the name many configs already use?~~ Closed as no longer relevant: workstream 2 does not keep the old paths, so the preset is published only at `tailwind`.
